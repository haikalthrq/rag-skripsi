1. GAMBARAN UMUM PROJECT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Ini adalah project SKRIPSI mahasiswa S1 yang membangun dan mengevaluasi sistem
RAG (Retrieval-Augmented Generation) berbasis dokumen statistik BPS Indonesia.

Nama folder   : rag-skripsi
Bahasa        : Python 3.11.9
OS            : Windows

Tujuan akhir penelitian:
  - Membandingkan 3 metode chunking (element_based, maxmin_semantic, recursive)
  - Menggunakan embedding Qwen3-Embedding-4B-GGUF
  - Generator: Qwen3-4B-Instruct-2507-FP8 (HuggingFace transformers)
  - Vector DB: ChromaDB
  - Evaluasi retrieval: Precision@k, Recall@k, MRR  (NDCG tidak dipakai)
  - Evaluasi generasi: BLEU, ROUGE-L Recall (RAGAS sementara tidak dipakai)

4. PIPELINE RETRIEVAL GROUND TRUTH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Pipeline 2 tahap (versi v3, menggantikan pipeline v1 lama yang 3 tahap):

TAHAP 1 — build_candidates_v3.py  (scripts/build_candidates_v3.py)
  Input  : qa_gold_standard_rag_bps_30qa_fixed_narrative_revised.xlsx
           + data/chunked/{method}/*.json
  Output : retrieval_relevant_chunks_candidate_v3_evidence_aware.xlsx/.csv
           summary_candidate_v3_evidence_aware.txt
           validation_candidate_v3_after_narrative_revision.txt
  Fungsi :
    - Scan SEMUA chunk per query × method
    - Hitung evidence score & tentukan match_type per chunk
    - Pre-filter top-10, lalu pilih top-5 terbaik per grup
    - Re-verifikasi semua flag dari chunk_text akhir (verify_and_fix_candidate)
    - Jika tidak ada kandidat relevan → buat baris "not_found" placeholder
    - Hasilkan kolom boolean eksplisit: has_gold_value, has_row_label, dll.
    - Generate laporan validasi ke summary .txt
  Jalankan: python scripts/build_candidates_v3.py [--top_k 5 --pre_k 10]

  Sistem scoring TABLE QA (evidence_type = table_row_column):
    gold_value_found   +5  (sinyal terpenting)
    page_match         +3
    row_label_found    +3
    col_label_found    +3
    table_id_found     +2
    anchor_found       +1
    evidence_text_found+1
  match_type TABLE:
    exact_table_evidence    → gv + rl + cl semua ditemukan → suggested=2, high
    partial_table_evidence  → gv ATAU (rl+cl) ditemukan   → suggested=1, medium
    keyword_only            → hanya sebagian sinyal kecil  → suggested=0, low
    not_relevant            → tidak ada sinyal → DIBUANG (tidak masuk kandidat)

  Sistem scoring NARRATIVE QA (paragraph, bullet, paragraph_table):
    evidence_text_found +5
    gold_answer_kw      +3  (word_overlap ≥50% kata ≥4 karakter dari gold_answer)
    anchor_found        +2
    question_kw         +2  (word_overlap ≥50% kata ≥4 karakter dari question)
    page_match          +1
    gold_value_pt       +1  (hanya paragraph_table)
  match_type NARRATIVE:
    exact_narrative_evidence   → evidence_text exact ditemukan → suggested=2, high
    partial_narrative_context  → ga_kw AND anc_found (keduanya harus ada) → suggested=1, medium
    keyword_only               → hanya sebagian sinyal (termasuk q_kw saja) → suggested=0, low
    not_relevant               → tidak ada sinyal → DIBUANG

  PERUBAHAN dari versi sebelumnya:
    partial rule lama: (ga_kw AND anc) OR score>=5  ← dihapus
    partial rule baru: ga_kw AND anc_found SAJA
    → q_kw saja atau ga_kw saja TIDAK bisa masuk partial
    → score>=5 shortcut dihapus karena bisa promosi ga_kw+q_kw tanpa anchor

  reason field NARRATIVE (detail per kata):
    Sekarang menampilkan kata-kata yang cocok + count, bukan hanya "found"
    Contoh: gold_answer_kw=16/30 [nilai, konstruksi, yang, ...]; question_kw=8/13 [...]

  Matching rules penting:
    label_match_strict : word-boundary matching (mencegah "Riau" match "Kepulauan Riau")
    gold_value_variants: normalisasi angka (titik ribuan, koma desimal, dll.)
                         TIDAK memakai fallback v in tn (mencegah false positive)

5. ATURAN ANOTASI LABEL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Label 2 — RELEVAN UTAMA
  Tabel  : chunk memuat relasi row_label + col_label + gold_value secara jelas
           (semua 3 flag has_gold_value + has_row_label + has_column_label = True)
  Narasi : chunk memuat klaim utama yang CUKUP untuk menjawab question
  JANGAN beri label 2 hanya karena ada keyword/angka tanpa konteks yang jelas

Label 1 — PENDUKUNG
  Chunk memuat informasi relevan sebagian, bukan bukti utama
  Bisa dipakai sebagai konteks tambahan RAG

Label 0 — TIDAK RELEVAN
  Chunk tidak memuat bukti atau konteks yang relevan sama sekali

needs_review — PERLU REVIEW ULANG
  Chunk ambigu, perlu diperiksa lebih lanjut sebelum diberi label final

PENTING:
  - Label TIDAK boleh ditetapkan otomatis oleh script
  - Harus dilakukan validasi manual oleh peneliti
  - suggested_label di kandidat adalah SARAN dari algoritma, bukan label final
  - Label 2 hanya untuk chunk yang benar-benar bisa menjawab question

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

File    : src/streamlit/app.py
Jalankan: streamlit run src/streamlit/app.py
         (JANGAN python app.py — itu bukan cara yang benar!)

Fitur app (versi terkini):

  DATA & RESUME
  - Load dari retrieval_relevant_chunks_candidate_v3_evidence_aware.xlsx
  - Merge otomatis dengan qa_gold_standard untuk tampilkan full question,
    gold_answer, evidence_text, table_id, row_label, col_label, dll.
  - Auto-resume: jika retrieval_labels_final.xlsx sudah ada, label yang
    sebelumnya disimpan akan dimuat kembali
  - Kolom yang di-restore saat resume: label_0_1_2, annotator, rationale
    (rationale persisten walau Streamlit restart)
  - Kolom rationale selalu diinisialisasi kosong di _load_fresh() agar
    df.loc[...] = new_rat tidak crash saat kolom belum ada

  NAVIGASI
  - Navigation bar atas dan bawah: tombol ◀ dan ▶ dengan info grup
  - Display number: "Q1 / 30" bukan raw query_id (karena ID tidak berurutan)

Metodologi Kandidat Anotasi — Oracle Pooling (bukan Retrieval Pooling):
  Kandidat anotasi (build_candidates_v3.py) menggunakan text-matching terhadap
  QA gold (gold_value, row_label, dll.) — BUKAN dari ChromaDB retrieval.
  Alasan: menghindari circular dependency (ground truth dari output sistem sendiri)
  Bedanya dengan retrieval pooling standar:
    Retrieval pooling: retrieve top-k dari setiap metode → pool → label
    Oracle pooling:    scan semua chunk vs QA gold → scoring → pool → label
  Keunggulan: bisa mendeteksi false negative (chunk yang seharusnya diambil
              tapi gagal di-retrieve oleh ChromaDB)

Keterbatasan per metode chunking (temuan dari quick eval 5 QA):
  element_based:
    - OCR corruption nilai tabel decimal (koma hilang → angka utuh)
    - Cross-doc interference: chunk dokumen lain mendominasi top-k untuk query numerik
    - Definisi pendek (<200 char) tidak kompetitif vs chunk tabel dengan keyword
    - Bilingual table rows: unstructured.partition_pdf tidak bisa memfilter kolom
      bahasa Inggris di layout dua kolom → baris tabel bilingual tetap masuk chunk
  maxmin_semantic:
    - Cluster terlalu besar untuk appendix tabel → embedding dilusi
    - Tabel Lampiran 1,3 berisi banyak topik berbeda → ranked >30 untuk query spesifik
  recursive:
    - Terbaik untuk nilai numerik tabel (ekstraksi teks, bukan OCR)
    - Lemah untuk pertanyaan definitif yang membutuhkan paragraf ringkas

Evaluasi retrieval menggunakan:
  Precision@k : berapa banyak dari k hasil teratas yang relevan
  Recall@k    : berapa banyak dokumen relevan yang berhasil ditemukan dalam k
  MRR         : Mean Reciprocal Rank — posisi dokumen relevan pertama
  NDCG        : TIDAK DIPAKAI dalam penelitian ini

Evaluasi generasi menggunakan:
  BLEU        : sentence-level via sacrebleu.sentence_bleu()
                hasil di-normalize ke 0–1 (sacrebleu native: 0–100)
  ROUGE-L     : recall mode via rouge_score.rouge_scorer.RougeScorer
                mengukur longest common subsequence recall
  Dependencies: pip install sacrebleu rouge-score

13. ANALISIS: SKIP RETRIEVAL EVAL → LANGSUNG GENERATION EVAL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PERTANYAAN: Bisakah skip anotasi manual + evaluasi retrieval dan langsung ke
            evaluasi generasi?

JAWABAN: BISA — tapi dengan konsekuensi metodologis yang perlu dipahami.

─────────────────────────────────────────────────────────────────────────────
APA YANG BISA DILAKUKAN TANPA RETRIEVAL GROUND TRUTH:
─────────────────────────────────────────────────────────────────────────────

  BLEU & ROUGE (100% bisa tanpa GT retrieval):
    Input: question → RAG pipeline → generated_answer vs gold_answer
    Tidak butuh chunk labels sama sekali.
    Mengukur kemiripan teks jawaban dengan referensi.

  RAGAS metrics yang BISA tanpa GT retrieval:
    answer_relevancy      — apakah jawaban relevan dengan question
    faithfulness          — apakah jawaban sesuai retrieved context
    answer_correctness    — apakah jawaban secara faktual benar (vs gold_answer)

  RAGAS metrics yang TIDAK BISA tanpa GT retrieval:
    context_recall        — butuh tahu chunk mana yang "seharusnya" di-retrieve
    context_precision     — butuh labeled ground truth chunks

─────────────────────────────────────────────────────────────────────────────
KONSEKUENSI JIKA SKIP RETRIEVAL EVAL:
─────────────────────────────────────────────────────────────────────────────

  1. TIDAK BISA bandingkan 3 metode chunking di level retrieval
     (Precision@k, Recall@k, MRR per metode tidak tersedia)

  2. Perbandingan chunking hanya bisa dilakukan di level generasi
     → "metode A menghasilkan jawaban lebih baik dari metode B"
       tanpa tahu KENAPA (apakah karena retrieval lebih baik atau bukan)

  3. Dari sisi metodologi skripsi:
     - RAG = Retrieval + Generation
     - Jika hanya evaluasi generation: penelitian kurang menjelaskan
       kontribusi masing-masing komponen
     - Reviewer/pembimbing bisa mempertanyakan validitas hasil

  4. Alternatif tengah: anotasi SUBSET kecil (misal 1-2 query per doc = ~30
     baris) untuk tetap bisa hitung retrieval metric, sambil tetap jalan
     generation eval. Lebih cepat dari anotasi penuh 412 baris.

─────────────────────────────────────────────────────────────────────────────
REKOMENDASI:
─────────────────────────────────────────────────────────────────────────────

  Jika WAKTU TERBATAS:
    → Lakukan anotasi subset ~60-90 baris (1 query × 3 method per dokumen)
    → Tetap bisa hitung retrieval metric (terbatas)
    → Langsung paralel mulai generation eval

  Jika INGIN SKIP TOTAL retrieval eval:
    → Bisa — pakai BLEU, ROUGE, RAGAS (answer_relevancy, faithfulness,
      answer_correctness)
    → Akui di metodologi skripsi bahwa retrieval eval tidak dilakukan
    → Fokus evaluasi ke kualitas jawaban akhir (end-to-end)

  Jika INGIN LENGKAP:
    → Anotasi semua 412 kandidat (estimasi: 2-4 jam dengan Streamlit app)
    → Lalu jalankan semua evaluasi
